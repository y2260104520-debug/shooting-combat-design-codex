# Problem Definition

## 目的

防止把现象、原因和方案混在一起。

## 六层定义

| 层级 | 问题 |
|---|---|
| 现象 | 玩家或数据发生了什么？ |
| 问题 | 为什么这个现象值得处理？ |
| 原因假设 | 什么机制可能导致它？ |
| 目标 | 希望玩家行为或系统结果变成什么？ |
| 约束 | 哪些东西不能改、成本边界是什么？ |
| 方案 | 用什么手段改变原因或结果？ |

## 判断规则

- 用户说“X 太强”只是现象或结论，不自动等于根因。
- 用户说“把 Y 降低”已经是方案，先回到目标和原因。
- 一个问题至少能描述“谁、在什么场景、发生什么、为什么不好”。
- 不能验证的原因只能叫假设。
- 若多个原因都可能成立，先设计能区分它们的验证方式，不同时改多个参数。

## 快速检查

1. 当前讨论的是现象还是原因？
2. 目标是否可观察？
3. 方案是否直接作用于根因？
4. 有没有更小的改动？
5. 方案失败时，如何区分判断错和参数不够？
