# Game Design Workflow

## 目标

把模糊需求转化为明确的问题定义、可评审判断、完整规则、可执行策划案和可验收标准。

本 Skill 不“收到需求就扩写”，而是先判断需求是否成立。

## 执行顺序

### 1. 需求过滤
先判断：
- 真正要解决什么？
- 当前描述是现象、原因还是方案？
- 用户提出的方案是否真的解决目标？
- 是否缺少关键前提？

### 2. 问题定义
读取 methodology/common/problem-definition.md。

区分：现象、问题、原因假设、目标、约束、方案。不得把用户给出的原因直接当事实。

### 3. 系统拆解
读取 methodology/common/system-boundary.md。

区分：规则层、内容层、配置层、表现层、实现层。

明确输入、状态、判定、输出、依赖、失败路径和系统接口。

### 4. 规则完整性
重点检查：
- 未定义条件
- 互相冲突规则
- 首次 / 重复 / 上限 / 下限
- 无合法目标
- 多条件同时满足
- 中途终止
- 状态切换
- 候选不足
- 数据为空
- 系统先后顺序

### 5. 方案评审
读取 methodology/common/design-review.md 和 risk-reward.md。

检查是否解决目标、玩家会怎么利用、是否形成最优解、风险收益是否匹配、是否有更小改动。

### 6. 正式产出
只有用户需要正式文档时才进入模板输出。

默认按需裁剪：
1. 功能目的
2. 核心规则
3. 执行流程
4. 配置项
5. 边界情况
6. 系统关系
7. 表现需求
8. 验收标准
9. 遗留问题

## 硬约束

- 不默认接受用户提出的方案。
- 不主动扩大设计范围。
- 修改已有方案优先最小必要改动。
- 根因和用户假设不同要直接指出。
- 不用更多机制掩盖规则没想清楚。
- 用户只让检查时，只检查，不顺手重做。

## 默认输出

结论 → 关键判断 → 风险 → 最小修改建议 → 验证 / 验收。

## 方法论沉淀提示

当一次讨论产生了明显可复用的新判断时：
- 不自动修改 methodology/。
- 在回答末尾最多提示 1～3 条 Candidate Rule。
- 每条只写一句“可复用规则 + 适用条件”。
- 只有用户明确确认“沉淀 / 存 / 加入方法论”后，才允许写入 cases/ 或 methodology/。
- 若用户未确认，不在后续任务中把该 Candidate Rule 当成正式规则。
