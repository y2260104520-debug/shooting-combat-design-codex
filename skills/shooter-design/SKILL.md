# Shooter Combat Design

## 主链路

现象 → 战斗问题 → 发生场景 → 影响指标 → 根因假设 → 生态影响 → 方案 → 副作用 → 验证方法

## 1. 先定义场景

优先确认：交战距离、单挑/多人、先手/接战、腰射/ADS、移动状态、TTK 档位、目标移动强度、地图是否高频提供该场景。

没有场景，单个数值结论通常没有意义。

## 2. 枪械分析

读取 combat-model、weapon-analysis、weapon-ecology。

根据问题检查：

理论效率：伤害、射速、STK / BTK、理论 TTK、伤害衰减。

实战兑现：命中率、后坐力、散布、目标移动、ADS、首发精度、连射稳定性、有效弹匣。

支付成本：换弹、机动、开镜时间、腰射、操作难度、距离短板。

生态：优势距离、劣势距离、是否侵蚀其他武器、是否跨多个场景保持高兑现率、是否形成结构性上位。

理论 TTK 正常不代表武器正常。若 eTTK 长期逼近理论 TTK，同时场景覆盖宽、支付成本低，应优先检查结构性泛用。

## 3. 技能分析

读取 methodology/shooter/skill-analysis.md。

判断：
1. 解决什么战斗压力。
2. 在什么场景成立。
3. 直接解决还是创造条件。
4. 是否改变交战时间或距离。
5. 是否创造击杀窗口。
6. 是否帮助兑现武器优势。
7. 释放风险。
8. 反制窗口。
9. 高低端收益差异。
10. 是否形成必选或 Meta 单一化。

## 4. 3C

读取 methodology/shooter/3c-analysis.md。

先区分：
- Control：输入、灵敏度、响应曲线、Aim Assist
- Character：速度、加速度、制动、空中控制、重力、状态切换
- Camera：FOV、ADS 过渡、镜头 Kick、回正、Shake、滞后

不要把“枪不好用”默认归因于枪械参数。

## 5. UE / Lyra / GAS

策划链路优先：

输入 → 状态判断 → 激活 → 表现 → 结算 → 结束 → 冷却

说明每个参数或模块对战斗体验的影响。

## 6. 验证

读取 methodology/shooter/validation.md。

重要结论至少给出：假设、控制变量、测试场景、指标、预期变化、失败判定。

## 硬约束

- 不从“AR 太强”直接跳到“加后坐”。
- 必须区分理论 TTK 与实战 eTTK。
- 强度必须结合交战距离。
- 泛用性本身就是强度。
- 优势必须看是否能稳定兑现。
- 修改参数前判断影响哪些玩家、距离和武器。
- 必须考虑高低端差异、反制和 Meta 风险。
- 修改已有设计优先最小必要调整。

## 方法论沉淀提示

当一次分析产生值得复用的新判断时：
- 不自动修改 methodology/。
- 回答末尾最多提示 1～3 条 Candidate Rule。
- Candidate Rule 必须写明适用场景或成立条件，不能写成无边界的绝对规则。
- 用户确认后，优先先进入 cases/shooter/ 保留上下文。
- 只有经过验证或用户明确确认其通用性后，才升级到 methodology/shooter/。
